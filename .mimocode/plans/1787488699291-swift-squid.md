# Migración del backend: Railway → Cloudflare Workers (free plan)

## Objetivo
Reescribir el backend Express+Prisma (hoy en Railway, `backend/`) como un **Cloudflare Worker** desplegable en el free plan, conservando **exactamente** el mismo contrato de API que consume el dashboard (`task-dashboard`), y **reutilizando la misma base de datos Postgres (Neon)** sin migración de esquema ni de datos.

**Alcance confirmado por el usuario:**
- Se implementan **solo** los endpoints CRUD + auth (ver contrato abajo).
- Se **excluyen** los endpoints de AI/Python (`/api/evaluate`, `/api/generate-pptx`, `/api/open-file`, `/api/interpret-apk`, `/api/research/sentiment`, `/api/search-product`, `/api/search-app-info`). Se responderá `404`/`501`, no se implementan.

## Restricción técnica clave (motiva toda la arquitectura)

Workers **free** no permite salida TCP ni WebSockets → **no se puede usar Prisma** ni el driver `pg`. La única vía para conservar el Postgres (Neon) es el **Neon serverless HTTP driver** (`@neondatabase/serverless`, función `neon()`, usa `fetch`/HTTPS) — documentado explícitamente como soportado desde Cloudflare Workers. Se escribe **SQL crudo** en el Worker contra las **mismas tablas y esquema** existentes.

**Además:**
- `bcrypt` (v6, paquete nativo) NO corre en Workers → usar `bcryptjs` (JS puro) para verificar los hashes bcrypt ya guardados en Postgres (compatibles).
- `jsonwebtoken` (depende de `node:crypto`) NO corre de forma fiable → firmar/verificar JWTs HS256 con **Web Crypto API** (HMAC-SHA256, mismo `JWT_SECRET`, mismo exp 24h) para que los tokens existentes sigan válidos.

## Contrato de API que el Worker debe cumplir (sin cambios)

Auth vía `Authorization: Bearer <token>` salvo rutas públicas.

| Método | Ruta | Acceso | Respuesta |
|---|---|---|---|
| GET | `/api/health` | público | `{status:'ok', timestamp}` |
| POST | `/api/auth/login` | público | `{user, token}` (sin `password`) |
| POST | `/api/auth/register` | público | 403 `{error:'Public registration is currently disabled'}` |
| GET | `/api/auth/me` | auth | `{user}` (sin `password`) |
| GET | `/api/app-data` | auth | AppData completo |
| POST | `/api/app-data` | auth | `{success:true, data}` |
| POST | `/api/snapshot` | auth | `{success:true, snapshotFile}` |
| GET | `/api/snapshots` | auth | `{snapshots:['YYYY-MM-DD',...]}` |
| GET | `/api/snapshots/:date` | auth | `{...AppData, snapshotDate}` (404 si no existe) |
| GET | `/api/users` | ADMIN | `{users}` |
| PATCH | `/api/users/:id/role` | ADMIN | `{user}` |
| DELETE | `/api/users/:id` | ADMIN | `{success:true}` |
| GET | `/api/research-reports` | auth | `{reports}` |
| POST | `/api/research-reports` | auth | `{success, report}` |
| GET | `/api/research-reports/:id` | auth | report (404) |

AppData shape (de `data-store-db.js::toAppDataPayload`): `{projects, members, tasks, statuses, priorities, scorecards, insights, lastUpdated}`. V.dirnit reminders con `status 'in_testing' ↔ 'in-testing'` en **task.status y status.id** (no en backlog/evaluating/reporting/done); `createdAt`/`week`/`deadline` → ISO strings; `tags`/`highlights`/etc. = objetos JSON ya parseados; `lastUpdated` = `new Date().toISOString()`.

## Contratos de auth/errores (espejo exacto de server.js)

- Middleware: paths públicos = `/api/health`, `/api/auth/register`, `/api/auth/login`. Sin header → 401 `{error:'No token provided'}`. Token inválido → 401 `{error:'Invalid or expired token'}`.
- `authorize('ADMIN')` (3 rutas users): sin user → 401 `{error:'Unauthorized'}`; rol ≠ ADMIN → 403 `{error:'Forbidden: Insufficient permissions'}`.
- Login inválido → 401 `{error:'Invalid email or password'}`.
- Error handler final → 500 `{error: message, stack?}`.

## Restricciones de datos a preservar (gotchas)

- `Member.email` es `@unique` → mantener el fallback `${id}@example.com` cuando el email del member guardado viene vacío (igual que `data-store-db.js`).
- **JSONB round-trip**: Neon HTTP devuelve columnas jsonb ya como JS (NO re-serializar). Al escribir, enlazar siempre con `JSON.stringify(value)` (Neon lo requiere).
- **DateTime**: Neon envía timestamps como ISO strings — pasarlos tal cual, NO `new Date()` de nuevo (evita drift de zona horaria).
- **Transaccionalidad de `POST /api/app-data`**: Prisma usaba `$transaction`; Neon HTTP es one-shot fetch. Usar el método `.transaction()` del driver con un array de sentencias SQL acotadas para atomicidad real (recomendado), o secuencial por-tabla con riesgo de escritura parcial. Snapshot save es una sola fila (ya atómica).
- El `DATABASE_URL` en el Worker debe apuntar al endpoint `.neon.tech` (accesible por HTTPS); el host directo solo-TCP rompería desde Workers. Mismo host y base que Railway, solo cambia el método de conexión.
- CORS en Worker: header manual `Access-Control-Allow-Origin` gate against `CORS_ORIGINS`, más `-Headers: Content-Type, Authorization`, `-Methods: GET,POST,PATCH,DELETE`, y `OPTIONS` → 204 temprano.
- No hace falta migración ni reescribir `prisma/schema.prisma` (el Worker usa SQL crudo; el esquema queda como está).

## Plan de implementación

### 1. Crear proyecto Wrangler nuevo (no tocar Railway aún)
Crear `backend/worker/` (proyecto self-contained, el backend de Railway queda como fuente de verdad y referencia).

Estructura:
```
backend/worker/
  wrangler.toml
  package.json              # deps: wrangler, @neondatabase/serverless, bcryptjs
  src/
    index.ts                # fetch handler: CORS → despacho de rutas → respuestas JSON
    routes.ts               # tabla de rutas + matching de rutas con params (espejo Express)
    auth.ts                 # JWT sign/verify (Web Crypto HMAC-SHA256) + bcryptjs compare
    sql/db.ts               # cliente neon() + helpers: findMemberByEmail, verifyPassword
    sql/load.ts             # loadAppData() — lee 7 tablas, mapea a AppData shape
    sql/save.ts             # saveAppData() — upserts por tabla (o .transaction())
    sql/snapshot.ts         # snapshot save/list/load
    sql/research.ts         # research reports CRUD
    schema.ts               # TS shapes: AppData, Member, Report (contrato de respuesta)
  test/http.test.ts         # (opcional) bloquea el contrato con bodies capturados
```

Propósito por archivo:
- `sql/db.ts`: únicamente `neon()` + queries param (injection-safe con template function).
- `sql/*.ts`: mapeo de shape JSON para mantener handlers finos.
- `auth.ts`: cero BD, crypto pura.

### 2. Implementar handlers como despacho de Worker

Reproducir la lógica de server.js/auth.js/data-store-db.js:
- **Login**: `SELECT * FROM Member WHERE email=$1` (parametrizado), `bcryptjs.compare`, devolver `{user, token}` quitando `password`.
- **Register**: hard return 403.
- **Auth middleware** con `publicPaths`; `authorize('ADMIN')` en `/api/users*`.
- **GET /api/app-data**: 7 queries en paralelo con el mismo `orderBy` de Prisma (projects.createdAt asc, members.joinedAt asc, tasks.createdAt asc, statusConfig.order asc, priorityConfig.defaultWeight desc, scorecards.week asc, insights.week asc). Mapear exactamente igual a `toAppDataPayload`.
- **POST /api/app-data**: upsert completo de las 7 tablas (vía `.transaction()` recorriendo `model.upsert` equivalente) con el fallback de email.
- **Snapshots**: list (`order by snapshotDate desc` → array de `'YYYY-MM-DD'`), save (upsert por snapshotDate, devuelve `` `${today}.json` ``), load (merge `{...jsonPayload, snapshotDate}`).
- **Research reports**: list / upsert-por-id / get-by-id, columnas jsonb como JSONB params.
- **Health**: público.

### 3. wrangler.toml recomendado

```toml
name = "workflow-nhan-backend"
main = "src/index.ts"
compatibility_date = "2024-01-01"
workers_dev = true

[variables]
DATABASE_URL = "<mismo Neon host que Railway>"
JWT_SECRET = "<mismo secreto>"
CORS_ORIGINS = "https://<dominio-dashboard>"

[features]
bindings = ["sql"]
```

Ejemplo del core DB (estilo en `src/sql/db.ts`):
```ts
import { neon } from "@neondatabase/serverless";
let sql: ReturnType<typeof neon>;
export const db = () => (sql ??= neon(process.env.DATABASE_URL!));
export const findMemberByEmail = async (email: string) =>
  db()`SELECT * FROM Member WHERE email=${email}`; // template: injection-safe
```

### 4. Pruebas locales

- `cd backend/worker`
- `npm install` + ejecutar el worker en local con **Wrangler local runtime** (`wrangler --local`, o el dev server de ndcnodepe adecuado) — servidor local en `http://127.0.0.1:8787`.
- Poner `VITE_API_URL=http://127.0.0.1:8787` + `DATABASE_URL`/`JWT_SECRET`/`CORS_ORIGINS` en el entorno local del worker.
- Probar GET/POST app-data, snapshot roundtrip, auth login/me/users contra el Postgres real. Consulta **igual** a `/api/app-data` contra el worker y contra el backend Railway actual y comparar payloads.

### 5. Verificación de extremo a extremo

1. Local: arrancar worker, curl cada endpoint de contrato (health, login con un usuario admin real, me, app-data GET/POST, snapshot save/list/load, users routes con y sin rol ADMIN).
   - Login válido → 200 `{user, token}`. Sin token en `/api/app-data` → 401 exacto.
2. Comparar shape de respuesta entre **new worker local** y **backend Railway** (misma DB) para `/api/app-data` — deben ser idénticos bytee a byte (assertiones de shape en `test/http.test.ts`).
3. Después de desplegar:
   - `wrangler deploy` al free plan.
   - Superponer `VITE_API_URL` del dashboard (build de producción) al URL `*.workers.dev`.
   - Smoke test paralelo: correr ambos backends, verificar misma respuesta de `/api/app-data`, y solo entonces apagar/mirar la ruta Railway.
   - Subir AppData, guardar snapshot, restaurar snapshot, login/logout desde el dashboard desplegado.
4. Limpiar secreto: `DATABASE_URL`, `JWT_SECRET`, `CORS_ORIGINS` solo como Worker secrets variables de entorno, jamás en repo.
